# 外部插件（规划中）

> 状态：方案设计中，尚未实现。本页描述目标与设计方向，完整计划在仓库的 `docs/plugin-plan.md`。

## 要解决的问题

把智能体接到一条流水线上时，它需要的不只是读写文件和跑 shell，而是接入流水线已有的能力：

- **看当前执行的日志**：某个构建、部署或任务的实时日志，能按游标继续读。
- **查监控**：指标、告警、最近一次发布的状态。
- **执行某个环节**：触发一次构建、重跑一个阶段、回滚到某个版本。
- **把环节串起来**：拿到结果后判断下一步，写回任务评论或进度。

这些能力属于外部系统，不应该写进执行引擎，也不适合全部塞进平台工具。它们需要一种**插件**接法：定义里声明插件，运行时把插件工具并入模型循环，权限、超时和审计仍由引擎统一管。

## 设计结论

**插件就是一个 MCP 服务，加一份本地声明。**

- 协议用 MCP（JSON-RPC 2.0）：`initialize`、`tools/list`、`tools/call`，支持 stdio 与 HTTP 两种传输。
- 不自造协议：日志、监控、CI 系统已经有 MCP 适配器，接入成本最低。
- 插件只提供**工具**，不提供消息来源，也不绕过工具白名单。
- 自运行与 Collab 共用同一套插件接口；区别只在插件由谁批准、在哪里运行。

## 定义长什么样（提案）

```json
{
  "plugins": [
    {
      "id": "ci",
      "transport": "stdio",
      "command": "npx",
      "args": ["-y", "@acme/ci-mcp"],
      "env": ["CI_URL", "CI_TOKEN"],
      "allow": ["logs_tail", "metrics_query", "stage_run"],
      "timeoutMs": 30000,
      "maxOutputBytes": 65536
    }
  ]
}
```

| 字段 | 说明 |
| --- | --- |
| `id` | 插件标识，用于工具命名与审计 |
| `transport` | `stdio` 或 `http` |
| `command` / `args` | stdio 插件的启动命令 |
| `url` | http 插件的地址 |
| `env` | 允许从运行进程继承的环境变量名；不接受明文值 |
| `allow` | 允许模型调用的工具名；未列出的工具不进入工具清单 |
| `timeoutMs` | 单次工具调用超时 |
| `maxOutputBytes` | 单次结果上限，超出截断 |

模型看到的工具名带命名空间，避免不同插件重名：

```text
plugin__ci__logs_tail
plugin__ci__metrics_query
plugin__ci__stage_run
```

`tools/list` 返回的 `description` 与 `inputSchema` 直接映射成模型工具定义；引擎只暴露 `allow` 里的工具，插件新增的工具不会自动获得权限。

## 调用上下文

每次调用会带一份 `_meta` 上下文，插件不需要自己猜当前在做什么：

```json
{
  "runId": "run-...",
  "agentId": "worker-1",
  "threadId": "task-42",
  "turnId": "turn-...",
  "taskId": "task-42",
  "idempotencyKey": "turn:...:call_1",
  "deadline": "2026-11-06T10:45:00.000Z"
}
```

上下文里不放模型密钥、平台令牌或完整环境变量。插件需要的外部凭据，只能通过 `env` 白名单从运行机器继承。

## 日志与长任务

- 插件在工具调用期间可以发 MCP 通知，引擎转成 `plugin-progress` 事件：终端里实时显示，Collab 路径写入运行日志。
- 长时间运行的任务不建议一直占着一次工具调用。更稳的方式是 `stage_run` 立即返回 run id，之后用 `stage_status` 轮询；智能体可以在不同轮次之间继续。
- 日志读取用游标：`logs_tail({ cursor })` 返回 `{ lines, cursor }`，下一轮从游标继续，不用重复拉全量。

## 安全边界

- **显式白名单**：插件、工具、环境变量都要在定义里写出来。
- **失败要响**：插件启动失败或工具缺失时启动即报错，除非显式声明可选。
- **超时与截断**：每次调用有超时和输出上限，避免一个卡住的插件拖垮整轮。
- **写操作幂等**：每个调用带 `idempotencyKey`；传输中断导致结果未知时，本轮以 `outcome_unknown` 收尾，不重试写操作。
- **审计**：记录插件 id、工具名、耗时与状态；不记录正文。
- **信任边界**：插件是运行机器上的独立进程，拥有启动它的用户权限。Collab 路径只允许平台批准的插件。

## 两种接入方式

| | 自运行 | Collab |
| --- | --- | --- |
| 插件来源 | 本地定义文件 | 平台定义，管理员批准 |
| 运行位置 | 启动智能体的机器 | worker / router 所在机器 |
| 凭据 | `env` 白名单或插件自己的配置 | 平台绑定变量名，值仍在运行机器 |
| 审批 | 文件即授权 | 插件注册表 + 定义审批 |
| 审计 | 本地日志 | 运行日志 + 平台审计 |

在 `--serve` 模式下，插件进程随服务常驻；一次性运行在结束时关闭插件。ANP router 里每个 agent 使用自己的插件实例，互不共享状态。

## 流水线场景映射

| 需求 | 插件工具 | 返回 |
| --- | --- | --- |
| 看当前执行日志 | `logs_tail` | 新增日志行与下一个游标 |
| 查构建状态 | `stage_status` | 阶段、结果、耗时、失败原因 |
| 查监控 | `metrics_query` / `alerts_list` | 时间序列或告警列表 |
| 触发环节 | `stage_run` | 运行 id，后续用状态工具跟进 |
| 发布 / 回滚 | `release_deploy` / `release_rollback` | 操作结果，带幂等键 |

智能体的职责不变：读任务、看日志、做判断、调用环节、把结论写回任务评论或进度。插件只是把外部能力变成可调用工具，不替智能体做决策。

## 分阶段

| 阶段 | 交付 |
| --- | --- |
| 1 | 定义里的 `plugins` 字段、MCP stdio 客户端、工具合并与本地测试 |
| 2 | 调用上下文、幂等键、进度事件、输出上限；自运行 `--serve` 常驻 |
| 3 | Collab 平台定义与插件注册表、变量绑定、审计 |
| 4 | HTTP 传输、流水线/监控适配器与端到端验收 |

## 现在能做什么

插件系统还没有落地。当前的替代做法：

- 用 `shell` 调用流水线已有的 CLI，例如 `git`、`gh`、内部发布脚本。
- 在 Collab 路径用平台工具读写任务、评论与文件，把结论留在平台。
- ANP router 里可以用 `http_fetch` 访问 allowlist 内的监控或流水线 HTTP 接口。

这些做法要么把外部系统当成命令字符串，要么需要预先写平台工具；插件系统要解决的是“任意外部能力以统一、可审计的方式接入”这件事。
